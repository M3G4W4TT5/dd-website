# Events integration and room inventory

The booking app reads the pretix organizer's events, excluding `PRETIX_EVENT_SLUG` (the rental series). An event series contributes only its actual subevents; a singular event contributes one occurrence. The public calendar omits inactive, unlisted and past occurrences. The rental availability API deliberately reads **all** other organizer events and subevents, including unpublished, inactive, hidden and sold-out dates. It blocks every overlapping one-hour rental slot for the full event interval. The only cancellation marker recognized for releasing occupancy is the organizer metadata property `ttd_cancelled=true` on the date. A missing event end time causes rental availability to fail closed instead of displaying unsafe hours.

The event detail route is `/events/{event-slug}/{date-id}`; singular events use `single`. Products and date quotas determine the displayed ticket state. Prices use date overrides when supplied. `ttd_image_url` can be configured as an organizer event/date metadata property with an HTTPS image URL; `ttd_description_da` and `ttd_description_en` provide description fallback for singular events. Series dates use pretix `frontpage_text`. No event schedule is synthesized on the website.

`PRETIX_API_BASE` is the server API origin; `PRETIX_SHOP_BASE` is the public pretix customer shop origin or path prefix. When pretix supplies an HTTPS event `public_url` on that origin, the app uses it so custom-domain event paths are respected. `PRETIX_API_TOKEN` remains server-only. Each date additionally requires pretix metadata `ttd_room_verified=true` after its room schedule is reviewed; singular events use event-level metadata. This prevents a newly added date from inheriting a checkout link automatically. The full-page purchase link targets the exact series date with `?subevent={id}` or the singular event shop. Checkout links stay hidden unless `PRETIX_EVENTS_CHECKOUT_ENABLED=true`, the public shop base is HTTPS, and the rental series/item are configured. The app also hides checkout for pretix test mode, unavailable tickets, presale windows, conflicting rental inventory and overlapping events, including unpublished ones. This is a **display gate**, not a transaction lock.

Before enabling checkout, the operator must:

1. Verify each event/date and its full end time in pretix, including private studio use and cancellations. Create the weekly activity as dated subevents and a standalone workshop as a singular event where appropriate.
2. Inspect the one-room schedule and any existing rental orders. Close all rental date quotas overlapping a paid event, including dates sold out or not publicly listed. Confirm the event has no existing rental collision, then mark that occurrence `ttd_room_verified=true` in pretix.
3. Configure product/date quotas, public shop domain, and a live payment provider in pretix. Test both a series date and singular event through the hosted checkout, payment, and resulting order.
4. Keep hourly rental sales disabled until a shared authoritative reservation system enforces both channels. The current `/api/quote` and `/api/preflight` only preview availability and do not reserve inventory. pretix Resources and Scheduling supports event series, but its guide says it has no useful features for singular events; scheduled resources also do not by themselves atomically reserve on-demand rental slots. Do not treat this catalog's overlap filter as a cross-channel booking guarantee.

If the room schedule cannot be kept exclusive in pretix, leave `PRETIX_EVENTS_CHECKOUT_ENABLED=false`. The public calendar can still describe the event, while the action clearly states why registration is unavailable.

## Local development examples

With `PRETIX_DEV_DRAFT_EVENTS=true` under `next dev`, unpublished pretix events in test mode appear in the calendar with no purchase action. This switch has no effect in production. The two supplied images in `public/events/` are mapped only to the local `dance-with-dd-dev` and `street-dance-workshop-dd-dev` slugs; event dates, prices and capacities still come from pretix.

The local pretix instance has `dance-with-dd-dev` as a series with 12 Wednesday dates from 2026-09-30 through 2026-12-16, 19:00–21:00 Copenhagen time, with a DKK 200 product and a separate 15-place quota for each date. `street-dance-workshop-dd-dev` is a singular event on 2026-10-03, 10:00–20:00 Copenhagen time, with a DKK 500 product and a 20-place quota. Both have Danish and English descriptions and remain unpublished in test mode. These records live in pretix, not in this repository; creating further Wednesdays requires adding dated subevents and quotas in pretix. The local "Booking availability (local read-only)" team's token can read all current and future organizer events, including unpublished dates, so new event room intervals can be included without changing its event scope. The team still has no order or customer access and cannot create events.

Booking management uses a separate read-only `PRETIX_MANAGE_API_TOKEN`. Its local Pretix team, "Booking management (local order read)", has **View all** orders for all current and future organizer events, without order-change permission. The real `/manage/booking` page and mutation routes are limited to the rental event/product configured by `PRETIX_EVENT_SLUG` and `PRETIX_ITEM_ID`; broader read-token scope does not make other event types manageable here. Install the read token as a server-only secret after migration, or create a replacement with the same scope if the VPS uses a fresh Pretix database. Create a separate least-privilege `PRETIX_MANAGE_WRITE_API_TOKEN` for tested order changes and refunds. Never put either in Git or a `NEXT_PUBLIC_` variable. `BOOKING_SELF_SERVICE_ENABLED` stays false until hosted Stripe, quota, email, and refund tests pass. The older eligibility endpoint remains read-only.

The deployment and launch gates for this flow are in [Booking management deployment](../../docs/BOOKING_MANAGEMENT_DEPLOYMENT.md).
