# Events integration and room inventory

The booking app reads the pretix organizer's events, excluding `PRETIX_EVENT_SLUG` (the rental series). An event series contributes only its actual subevents; a singular event contributes one occurrence. The public calendar omits inactive, unlisted and past occurrences. The rental availability API deliberately reads **all** other organizer events and subevents, including unpublished, inactive, hidden and sold-out dates. It blocks every overlapping one-hour rental slot for the full event interval. The only cancellation marker recognized for releasing occupancy is the organizer metadata property `ttd_cancelled=true` on the date. A missing event end time causes rental availability to fail closed instead of displaying unsafe hours.

The event detail route is `/events/{event-slug}/{date-id}`; singular events use `single`. Products and date quotas determine the displayed ticket state. Prices use date overrides when supplied. `ttd_image_url` can be configured as an organizer event/date metadata property with an HTTPS image URL; `ttd_description_da` and `ttd_description_en` provide description fallback for singular events. Series dates use pretix `frontpage_text`. No event schedule is synthesized on the website.

`PRETIX_API_BASE` is the server API origin; `PRETIX_SHOP_BASE` is the public pretix customer shop origin or path prefix. When pretix supplies an HTTPS event `public_url` on that origin, the app uses it so custom-domain event paths are respected. `PRETIX_API_TOKEN` remains server-only. Each date additionally requires pretix metadata `ttd_room_verified=true` after its room schedule is reviewed; singular events use event-level metadata. This prevents a newly added date from gaining payment access automatically.

## Event signup

The event description has a **Sign up / Tilmeld dig** button that opens the purple form on the same page. Sold-out, closed-sale and room-conflict occurrences have disabled actions. The form reuses `BuyerDetailsFields`, `DetailsConsent` and `SpringCheckbox` with the studio booking form. It collects one buyer's required name, email and phone, ticket quantity, separate optional unchecked TTD marketing consent, and required unchecked acceptance linking to the existing `/terms` document and `/privacy` policy. The terms content is intentionally unchanged in this implementation. There is no refund notice or setup-placeholder text on the form.

The summary shows the event/date/location and an updating DKK total. Quantity is limited by shared event availability, the product's available quota and min/max limits, without an additional application cap. Pretix order limits match each event's capacity (15 for Dance with DD and 20 for the workshop). Excess quantities are clamped to the allowed maximum and that maximum is shown in red. Product variations are not selectable through this form. If an event has several simple admission products, the form offers a ticket-type selector. Add-on/non-admission products are excluded.

`POST /api/events/checkout` validates the buyer, terms, quantity, exact product/date and displayed unit price, and re-fetches the catalog before any marketing request or handoff. Origin checking, a request-size bound, per-process rate limiting and no-store responses protect the endpoint. Marketing reuses the existing separate TTD double-opt-in list and never subscribes the other attendees; a marketing failure allows continuing to payment. The endpoint never creates an order or uses an order-write token.

After validation, the browser posts the chosen product/quantity and buyer `widget_data` into Pretix's native, randomly namespaced cart (`w/{16-character-namespace}/cart/add`), then continues to `checkout/start`. Name, email and phone are in POST fields, never query parameters. This uses the installed Pretix 2026.7 native widget/cart interface. Pretix calculates final prices, enforces sale/quantity/quota rules and reserves tickets in its own cart. If availability changes during the handoff, Pretix displays its cart error and returns to the shop for review instead of proceeding straight to checkout. The native cart may retain a partial selection after a quota conflict; no order or payment is silently created by this form.

Payment handoff remains blocked server-side unless `PRETIX_EVENTS_CHECKOUT_ENABLED=true`, the public shop base is HTTPS, the rental series/item are configured, the event is available outside test mode, and its room is verified. The form can be reviewed in local development with the final button and fields; submitting while the checkout gate is disabled produces the normal checkout-failure message. This is a **display/preflight gate**, not a transaction lock across room-rental and event sales.

### Required Pretix buyer and order settings

For each event, configure **Settings → General → Customer and attendee data** to require a phone number per order, not ask for attendee names or attendee emails, and use **Ask for Name, display like John Doe** as the name scheme (`full`). Email remains required once per order. In **Settings → Invoicing → Address form**, require the customer name and disable asking for a postal invoice address. In **Settings → General → Cart**, set the maximum number of tickets per order to the event capacity so one buyer can purchase all remaining places. Avoid smaller product limits unless explicitly required. Maintain each date's independent capacity quota. Keep **Customers can cancel their paid orders** disabled under **Settings → Cancellation**; organiser-initiated cancellation/refunds remain possible. The two existing private local test events have these buyer settings applied and still have `live=false`, `testmode=true`. A mode-600 settings snapshot is saved inside the private local Pretix data volume; it is not part of the repository.

Verification on 2026-09-26: the installed native cart reserved three tickets for the series date (DKK 600) and the singular workshop (DKK 1500), rejected exceeding the then-configured order limit (subsequently raised to each event capacity), and prefilled buyer name/email/phone with phone required. Only synthetic cart positions were created; they were removed and inventory restored. No orders, emails or payments were created by these cart tests. Hosted HTTPS payment, confirmation delivery and organiser refund verification remain part of the existing launch checks.

Before enabling checkout, the operator must:

1. Verify each event/date and its full end time in pretix, including private studio use and cancellations. Create the weekly activity as dated subevents and a standalone workshop as a singular event where appropriate.
2. Inspect the one-room schedule and any existing rental orders. Close all rental date quotas overlapping a paid event, including dates sold out or not publicly listed. Confirm the event has no existing rental collision, then mark that occurrence `ttd_room_verified=true` in pretix.
3. Configure product/date quotas, public shop domain, and a live payment provider in pretix. Test both a series date and singular event through the hosted checkout, payment, and resulting order.
4. Keep hourly rental sales disabled until a shared authoritative reservation system enforces both channels. The current `/api/quote` and `/api/preflight` only preview availability and do not reserve inventory. pretix Resources and Scheduling supports event series, but its guide says it has no useful features for singular events; scheduled resources also do not by themselves atomically reserve on-demand rental slots. Do not treat this catalog's overlap filter as a cross-channel booking guarantee.

If the room schedule cannot be kept exclusive in pretix, leave `PRETIX_EVENTS_CHECKOUT_ENABLED=false`. The public calendar can still describe the event, while the action clearly states why registration is unavailable.

## Local development examples

With `PRETIX_DEV_DRAFT_EVENTS=true` under `next dev`, unpublished pretix events in test mode appear in the calendar and expose the signup form for local UI review; their payment handoff remains blocked. This switch has no effect in production. The two supplied images in `public/events/` are mapped only to the local `dance-with-dd-dev` and `street-dance-workshop-dd-dev` slugs; event dates, prices and capacities still come from pretix.

The local pretix instance has `dance-with-dd-dev` as a series with 12 Wednesday dates from 2026-09-30 through 2026-12-16, 19:00–21:00 Copenhagen time, with a DKK 200 product and a separate 15-place quota for each date. `street-dance-workshop-dd-dev` is a singular event on 2026-10-03, 10:00–20:00 Copenhagen time, with a DKK 500 product and a 20-place quota. Both have Danish and English descriptions and remain unpublished in test mode. These records live in pretix, not in this repository; creating further Wednesdays requires adding dated subevents and quotas in pretix. The local "Booking availability (local read-only)" team's token can read all current and future organizer events, including unpublished dates, so new event room intervals can be included without changing its event scope. The team still has no order or customer access and cannot create events.

Booking management uses a separate read-only `PRETIX_MANAGE_API_TOKEN`. Its local Pretix team, "Booking management (local order read)", has **View all** orders for all current and future organizer events, without order-change permission. The real `/manage/booking` page and mutation routes are limited to the rental event/product configured by `PRETIX_EVENT_SLUG` and `PRETIX_ITEM_ID`; broader read-token scope does not make other event types manageable here. Install the read token as a server-only secret after migration, or create a replacement with the same scope if the VPS uses a fresh Pretix database. Create a separate least-privilege `PRETIX_MANAGE_WRITE_API_TOKEN` for tested order changes and refunds. Never put either in Git or a `NEXT_PUBLIC_` variable. `BOOKING_SELF_SERVICE_ENABLED` stays false until hosted Stripe, quota, email, and refund tests pass. The older eligibility endpoint remains read-only.

The deployment and launch gates for this flow are in [Booking management deployment](../../docs/BOOKING_MANAGEMENT_DEPLOYMENT.md).
