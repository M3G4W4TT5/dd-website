# Booking management deployment and launch gates

Booking management lives in `apps/booking/server`, with a dedicated management database. Web owns sessions, recovery requests, operations and authenticated webhook intake; a supervised worker owns authoritative reads, recovery/paid mail and rental transition reconciliation. [Operations](architecture/OPERATIONS.md) documents exact envs, migrations, container startup, queue recovery and backup/restore.

Recovery responses are generic. A matching paid or canceled rental receives a 15-minute one-use link; explicit POST creates an HttpOnly, host-only, SameSite=Lax one-hour session restricted to matching order codes, Secure in production. Pretix order secrets remain server-only. Paid rental confirmation derives recipient and language from Pretix, never the webhook/caller. Pending orders and event tickets receive no app rental confirmation.

Changes/refunds require the scoped session, correct rental product/event, consecutive one-hour positions and more than 24 elapsed hours before the first hour. Changes recheck live availability, unchanged duration/price and authoritative positions before writing. Cancellation requires one matching confirmed Stripe payment and initiates a full refund with cancellation; displayed/mail refund states remain pending/done/failed as returned by Pretix. The database lock serializes application writers; Pretix remains authoritative for quotas and direct admin changes.

Persisted operation intents survive lost responses. An ambiguous write blocks another write until authoritative reconciliation or explicit operator rejection after proof of no remote action. Duplicate/reordered webhook triggers are durable and deduplicated by provider notification ID; revision-based notification identity permits legitimate repeated state changes. SMTP uncertainty becomes an explicit ambiguous state without automatic resend. Receipt/invoice/ticket mail belongs to Pretix; custom rental management and lifecycle notices belong to the worker, using tagged no-reply From/envelope and monitored booking Reply-To. App changes suppress native Pretix change mail.

Use `BOOKING_DATABASE_URL`, `BOOKING_PUBLIC_BASE_URL`, scoped Pretix read/write tokens, webhook Basic credentials, recovery hash/payload keys and the dedicated booking-marketing bearer according to the web/worker env examples. Web receives no SMTP; worker receives no write token or marketing credential. Run scoped management migrations before runtime. Pretix runtime is non-superuser and uses `AUTOMIGRATE=skip`; deploy its separate migrator job first.

Hosted configuration and paid-sandbox verification remain outstanding. Configure authenticated HTTPS webhooks for relevant rental transitions; keep credentials out of URLs/logs/docs. Verify actual Stripe provider/refund behavior, payment pending versus paid notices, receipts versus custom confirmation, one/multiple/full-day intervals, recovery expiry/redemption/scope, concurrent/stale operations, response loss, quota/cross-channel contention, 24-hour/DST boundaries, accurate lifecycle mail and actual external delivery. Operator/admin changes must not send competing native/manual rental notices. [Owner checks F8–F12](architecture/OWNER_FOLLOW_UP.md) define acceptance. Keep self-service and checkout release gates disabled until they pass; local inventory/locks do not establish atomic cross-channel reservations.
