# Booking management: deployment and remaining work

## Current state (25 September 2026)

- `/manage/preview` is a development-only mock. Its booking start is signed by the server, and its change/cancel actions are checked against server time. It changes no pretix order, starts no refund, and sends no email.
- `POST /api/manage/eligibility` is read-only. Given an order code and order secret in the request body, it fetches the configured rental event's paid order and dated positions from pretix, determines the first booked hour, and compares it with the server clock. It returns `404` for an unknown order and fails closed if pretix, the token, or the order data is unavailable. It cannot authorize a mutation by itself.
- The local `PRETIX_MANAGE_API_TOKEN` belongs to the pretix team **Booking management (local order read)**. The team has `View all` orders for all current and future organizer events, with no order-change permission. Order reads were verified against the three current events. The token is stored only in the ignored `apps/booking/.env.local` file. The public availability token remains separate and has no order access.
- The app's eligibility route is intentionally limited to the rental event selected by `PRETIX_EVENT_SLUG` and `PRETIX_ITEM_ID`. Broader token permission does not make event-ticket bookings manageable or apply the studio's 24-hour policy to them.

## Before enabling real self-service

1. Implement the authenticated order-specific management page using the pretix order link/secret. Do not put the secret in application logs or analytics. Establish the lost-link recovery flow and rate limits described in the project specification.
2. Add separate server-side change and cancellation handlers. Each handler must **re-fetch the current pretix order and its dated positions immediately before its write**, verify the order secret, paid status, exact rental product, entire consecutive interval, and the cutoff using the server clock. Client time, client-submitted booked hours, and a prior eligibility response are never authorization. At exactly 24 elapsed hours or less before the first booked hour, reject the write. Recheck the cutoff after any awaited availability work and before the mutation.
3. Give a separate management-write pretix token only the order permissions needed for those handlers. Keep the existing read token read-only. Confirm pretix's own customer-facing change/cancellation controls cannot bypass the agreed cutoff through the order page or direct shop URLs.
4. For changes, check the full new interval and quota at commit time, retain the original booking if the change cannot complete, and handle concurrent requests. For cancellation, record the cancellation and initiate a full refund to the original payment method only when the order/payment state supports it. Make retries and repeated webhook deliveries idempotent; show the actual refund state rather than assuming completion.
5. Configure the paid, changed, and cancelled email content and sender described in [the email draft](BOOKING_CONFIRMATION_EMAIL.md). Send change/cancellation confirmation only after the pretix transition is recorded, and do not duplicate a pretix-generated message. Verify `noreply+booking@didde-mie.com` as From and `booking@didde-mie.com` as Reply-To on automated mail.
6. Test with synthetic paid sandbox orders: one hour and multiple hours; just before, exactly at, and after the 24-hour cutoff; Copenhagen daylight-saving changes; a changed browser clock; direct handler calls; stale availability; simultaneous changes; cancellation/refund failure and retry; and email delivery. No orders exist in the local test event yet, so this end-to-end gate remains open.

## VPS preview and release

- Deploy the booking app and pretix behind HTTPS. Set `PRETIX_API_BASE`, organizer/event/item identifiers, and the **server-only** `PRETIX_MANAGE_API_TOKEN` in the deployed secret store. Do not use a `NEXT_PUBLIC_` variable, commit a token, or copy the entire local `.env.local` file. If the pretix database is migrated, verify the token still works; if the VPS has a fresh database, create a replacement with the same intended scope. Recheck all-event order-read access after migration. `MANAGE_PREVIEW_SIGNING_KEY` is local development only.
- Keep the server clock synchronized and use the booked timestamps' offsets to compare instants; format customer-facing times in `Europe/Copenhagen`. The cutoff is **strictly more than 24 elapsed hours** before the first booked hour.
- Keep real checkout and self-service mutation disabled until pretix order writes, Stripe sandbox webhooks/refunds, SMTP, room inventory, and the checks above pass in the private HTTPS preview. See [Stripe and pretix setup](STRIPE_TEST_SETUP.md) and the [events guide](../apps/booking/EVENTS.md).
