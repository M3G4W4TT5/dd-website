# Booking management deployment and launch gates

## Implemented in the booking app

- `/manage` accepts the purchaser's email without disclosing whether an order exists. A matching paid or canceled studio order gets a 15-minute one-use access email. Redemption creates an HttpOnly, SameSite=Lax one-hour session scoped to the matching order codes. `/manage/booking?code=…` then displays the live pretix order, booked hours, amount, cancellation state, and refund state. It never places the pretix order secret in the browser.
- `POST /api/manage/booking` changes all rental hour positions in one pretix order-change operation, or asks the confirmed Stripe payment to refund in full with `mark_canceled`. Both actions require the scoped session, the exact configured rental event/product, consecutive one-hour positions, and strictly more than 24 elapsed hours before the first booked hour. Changes require live pretix availability, the same duration and total price, then re-read the order before the write. A PostgreSQL advisory lock serializes app-initiated changes for each order. Pretix remains the authority for quota and payment state.
- The separate write token and `BOOKING_SELF_SERVICE_ENABLED=true` are required for mutations. With the gate off, visitors can see their booking and contact the studio; no UI action pretends to change or refund it. `/manage/preview` remains a local mock and is not used by the real page.
- `POST /api/manage/pretix-webhook` accepts Basic-authenticated `pretix.event.order.paid` notifications for only the configured rental event. It re-reads the paid rental order from pretix, then sends an app management access email. `manage_paid_emails` suppresses ordinary duplicate webhook delivery. An SMTP success followed by a database failure can still cause a duplicate email on retry; both links remain short lived and one use. Do not expose webhook credentials in logs or documentation.

## Required configuration

1. Keep `PRETIX_MANAGE_API_TOKEN` read-only. Create a separate `PRETIX_MANAGE_WRITE_API_TOKEN` with only the order permissions needed for the change and payment-refund endpoints. Keep both server-only. Verify the exact scope and the provider value returned for a paid Stripe test order; the implementation currently accepts `stripe`.
2. Set the configured organizer, rental event, item, `PRETIX_API_BASE`, `SUBSCRIPTIONS_DATABASE_URL`, `SUBSCRIPTIONS_PUBLIC_BASE`, `CONTACT_BOOKING_ORIGIN`, `BOOKING_SMTP_PASSWORD`, and `MANAGE_RECOVERY_HASH_KEY` in the deployed secret store. Public app and pretix shop URLs must use HTTPS. Do not copy local `.env.local` wholesale.
3. Back up the separate application database, then apply [`apps/booking/subscriptions.sql`](../apps/booking/subscriptions.sql) to that database, never pretix's. It adds `manage_link_requests`, `manage_link_tokens`, `manage_sessions`, and `manage_paid_emails`. The additive SQL has been applied locally after a restricted backup at `/tmp/ttd-marketing-before-manage-sessions.sql`; repeat backup and migration on the hosted database. Do not recreate any volume.
4. Set `PRETIX_MANAGE_WEBHOOK_USER` and a random `PRETIX_MANAGE_WEBHOOK_PASSWORD` of at least 32 characters. Configure a pretix organizer webhook for `pretix.event.order.paid`, limited to the rental event, targeting `https://user:password@<booking-host>/api/manage/pretix-webhook`. Ensure the proxy forwards the Authorization header and this one route is reachable without interactive login. Pretix webhook payloads are only triggers; the app fetches the order itself. Configure pretix's background task queue or otherwise verify failed webhook retry on the hosted instance.
5. Decide email ownership before opening checkout: pretix can send the receipt/paid-order detail, while the app sends the separate confirmation and one-use management link from `booking@didde-mie.com`. Remove `{url}` claims that it opens the custom management page from the pretix template; `{url}` opens pretix. Avoid two messages both described as the sole confirmation. Verify From, Reply-To, language, duplicate handling, and inbox delivery with paid sandbox orders. See [booking email guide](BOOKING_CONFIRMATION_EMAIL.md).

## Private HTTPS sandbox checks before enabling self-service

- Place real sandbox paid rental orders of one, multiple, and full-day hours. Confirm the management email arrives, the link opens the app order page, a second redemption fails, and an unrelated order code is denied. Test no-match email responses and token expiry. There are no paid local test orders as of 25 September 2026.
- Change an order to a free interval of the same length and price. Verify every pretix position, quota, app display, and change email. Try stale availability, another simultaneous request, price change, mixed products, quota contention, and an API failure; the original booking must remain if the change is rejected. Confirm pretix's own customer-facing order controls cannot bypass the policy.
- Cancel a sandbox Stripe-paid order. Verify pretix status `c`, exactly one full refund to the original payment, accurate pending/done/failed display, Stripe state, repeated requests, and a provider error. The payment provider's actual refund behavior and `mark_canceled` support must be observed; no live refund has been exercised by this implementation.
- Test 24-hour boundary just before, exactly at, and after the cutoff; Copenhagen daylight-saving transitions; a changed browser clock; direct API calls without a session, with another order code, and with a forged Origin. Confirm the app rejects demo availability for writes.
- Test pretix paid webhook delivery, duplicate and failed deliveries, and app SMTP on the hosted HTTPS preview. Configure and verify post-change and post-cancellation messages in pretix; the current change call requests a pretix email and the refund API's notification behavior must be checked in sandbox. Make the rendered content agree with the actual order/refund state.
- Only then set `BOOKING_SELF_SERVICE_ENABLED=true`. Enabling hourly rental checkout additionally requires the shared room-reservation/collision control described in the [events guide](../apps/booking/EVENTS.md); the catalog overlap filter is not a transaction lock. Keep both gates false if any payment, refund, quota, email, or cross-channel inventory check fails. Also complete [Stripe setup](STRIPE_TEST_SETUP.md).

pretix references: [order change and refund API](https://docs.pretix.eu/dev/api/resources/orders.html), [webhooks](https://docs.pretix.eu/dev/api/webhooks.html), [email placeholders](https://docs.pretix.eu/guides/email/).
