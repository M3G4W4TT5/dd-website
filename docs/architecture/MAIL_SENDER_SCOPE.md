# Mail sender scope: owner checkpoint

Updated 29 September 2026. This is a current, bounded mail task record. Do not treat the older hosted narratives as proof of present mail state. No mail-release gate or public deployment is authorized by this document.

## Observed provider state

- The signed-in Purelymail Account Admin portal currently has **Restrict who users can send as** selected. It has an exact allow rule from `booking@didde-mie.com` to `noreply+booking@didde-mie.com` (prefix matching off) and an **all-users Default Purelymail rules: Allow** rule. The latter explicitly permits a user's own symbolic subaddresses when the domain feature is enabled. [Purelymail's sender-policy guide](https://support.purelymail.com/support/solutions/articles/159000433207-error-530-5-7-1-you-x-are-not-authorized-to-send-mail-as-y-) describes authorization of both envelope and visible From.
- The live Routing page shows **Symbolic Subaddressing enabled** for `didde-mie.com`. This contradicts the earlier checkpoint claim that it was disabled. The enabled feature and default send-as rule explain the prior accepted `booking+unapproved@didde-mie.com` probes on both new booking process credentials. This is an inference from the policy and observations, not a fresh SMTP test. [Purelymail's subaddressing guide](https://support.purelymail.com/support/solutions/articles/159000406702-symbolic-subaddressing) warns that disabling the feature stops tagged inbound delivery.
- The booking user's app-password list shows distinct `booking communications` and `booking worker` entries plus older `controlled mail` and `contact form` entries. Names and last-used indicators do not prove which systems still hold the older secrets. App passwords can be revoked individually, but Purelymail states they give full mailbox access; they are not process-specific send-as policies.
- In the repository, production booking communications and worker are the only booking application SMTP consumers. Booking web rejects SMTP credentials. Hosted Pretix has historically remained on Mailpit, and the primary service is not part of booking hosting. Local active process files are capture-only; `infra/local/retired-booking.env` still has legacy SMTP fields and must remain private. The current VPS runtime configuration needs a fresh owner-sudo inventory.

## Smallest exact-scope arrangement for owner review

**Proposed:** preserve inbound symbolic subaddressing and replace the all-users default send-as allowance with exact per-user own-address allowances, retaining the booking user's exact `noreply+booking@` exception. This changes account-wide outbound policy, so first inventory legitimate tagged sender use for every account user. If Purelymail cannot enforce these exact policies independently of its default symbolic rule, the fallback is to disable symbolic subaddressing for `didde-mie.com` and add an explicit inbound route for `noreply+booking@` to the monitored no-reply mailbox; that fallback also requires an inventory of every other tagged recipient because disabling symbolic routing can make those addresses bounce. Neither change should be saved until the owner selects it and the full policy is staged for review.

After a policy change, run the bounded positive and negative SMTP matrix below for **each** booking process credential. If any `booking+` or mixed header/envelope probe is accepted, the exact sender-scope requirement is still unmet. Preserve capture/controlled delivery and the single approved recipient; do not enable unrestricted mail to test this.

## Private owner sequence

1. Inventory all holders of the older booking app password outside Git: VPS runtime files and mounted services, Pretix runtime/migration mail settings, optional primary services, local processes/retired files, mail clients, schedulers and any other integration. Compare secret values only inside an owner-controlled root terminal; record service names and match/no-match, never values or hashes. Confirm whether `controlled mail` is the shared credential to retire and whether the older `contact form` entry is in use.
2. Keep the two new booking credentials in the communications and worker files, independently verify their mounted runtime files, and give Pretix its own credential only when its controlled recipient path is ready. Test every migrated consumer through a real delivered message to `dev@memoryone.eu`. Verify From, Return-Path, Reply-To, SPF, DKIM, DMARC and TLS in the receiving mailbox; SMTP acceptance alone does not prove delivery.
3. Use `python3 infra/check-mail-sender-scope.py booking --credential communications` and repeat for `worker` (and `pretix` only after migration). The script prompts privately, sends only synthetic messages to the approved recipient, and prints sanitized case outcomes. A denied case that is accepted is a failed scope check. Run contact/newsletter cases with their respective credentials when those consumers are in scope. Do not pass credentials in shell arguments, environment variables, logs or chat.
4. Verify direct replies reach monitored `booking@` and that `noreply+booking@` routes to a monitored mailbox. Use a controlled invalid-recipient test only after confirming a safe destination and operator handling; never use a real customer address. Record whether a bounce is observed by the operator and whether transactional failure alerts or marketing suppression are handled by the existing queue workflow. Do not infer reliable bounce monitoring from a single SMTP success.
5. Only after every authorized old-credential consumer is migrated and delivery is confirmed, revoke the identified shared app password in Purelymail. Run `python3 infra/check-mail-sender-scope.py booking --credential old-shared --auth-revoked` in the owner terminal and require authentication rejection. Do not delete the booking user or the older `contact form` credential without its separate inventory.

Record sanitized results in this checkpoint after execution: policy selected, positive/negative case outcomes per credential, migrated consumer list, delivery/header/reply/bounce evidence, revoked credential label and rejected authentication, and unresolved limits.
